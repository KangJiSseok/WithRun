# 리워드 가챠 제품 규칙 디자인

## 문서 범위

이 문서는 `docs/plans/2026-03-28-reward-gacha-screen-reward-design.md`의 후속 문서로,
기존에 미확정으로 남겨둔 **제품 규칙**만 정리한다.

이 문서에서 확정하는 범위는 아래와 같다.

- 포인트 사용 방식
- 꽝/당첨의 의미
- 재도전권 정책
- 일일 제한 방식
- 운영 노출 정책

이 문서는 아래 항목은 아직 확정하지 않는다.

- 상위/중간/꽝의 정확한 수치 확률
- 포인트 지급량의 정확한 수치
- DB 스키마 상세
- API 명세 확정안
- 구현 일정과 세부 개발 순서

## 전제

- 기존 화면/감정 설계는 유지한다.
- 핵심 UX는 **카드팩 개봉 직전과 카드 뒤집기 순간의 긴장감**이다.
- 이 가챠는 친절한 보상 회수 시스템이 아니라, **짧고 선명한 결과 확인 경험**을 제공해야 한다.
- 기존 웹 디자인 토큰 사용 원칙은 그대로 유지한다.

## 제품 규칙 방향

이 가챠의 규칙 설계는 아래 방향을 우선한다.

- 긴장감과 결과의 선명함을 유지한다.
- 실패를 자동 보정하지 않는다.
- 사용자가 복잡한 운영 정책을 학습하지 않아도 되게 한다.
- 일일 러닝 보상 루프 안에서 자연스럽게 소비되게 한다.

즉, 이 시스템은 누적 구제형이나 보장형 구조가 아니라,
**매번 독립적으로 결과를 확인하는 순수 가챠 구조**를 따른다.

## 포인트 경제 방향

- 가챠 포인트는 **러닝으로 모으는 일일성 재화**로 본다.
- 사용자는 러닝/미션/출석 등 제품이 제공하는 일일 활동을 통해 포인트를 모은다.
- 포인트는 장기 투자 재화라기보다 **그날 얻고 그날 써보는 재화**에 가깝다.
- 기본 규칙은 **1포인트 = 1회 가챠**를 기준으로 설계한다.

이 구조의 목적은 많은 포인트를 쌓아 한 번에 폭발시키는 데 있지 않다.
목표는 사용자가 “오늘도 한 번 열어볼까?”라고 느끼게 하는 것이다.

## 꽝과 당첨의 의미

- **꽝은 실제 꽝이다.**
- 꽝 결과는 다음 당첨을 위한 누적 게이지, 조각, 보장 포인트로 전환되지 않는다.
- 당첨은 희귀하게 유지하며, 그래서 의미를 갖는다.
- 상위 보상 희소성은 UX의 긴장감을 지탱하는 핵심 요소다.

이 가챠에서는 실패를 위로하기 위한 시스템을 기본값으로 두지 않는다.
사용자는 결과를 있는 그대로 받아들이고, 다음 시도 역시 독립된 기대감으로 접근한다.

## 보정 장치 비포함 원칙

다음 구조는 기본 시스템에 포함하지 않는다.

- 누적 게이지
- 천장 시스템
- 꽝 보상 조각
- 연속 실패 보정 확률
- 실패 후 추가 위로 재화 지급

이 원칙은 “꽝이면 꽝”이라는 제품 규칙을 흐리지 않기 위해 필요하다.

## 재도전권 정책

- 재도전권은 **기본 시스템에 넣지 않는다.**
- 재도전권이 기본 흐름에 포함되면 꽝의 의미가 약해지고, 결과의 선명함이 흐려진다.
- 초기 제품 규칙은 **재도전권 비포함**을 기본값으로 삼는다.
- 향후 이벤트성 기획이 필요하면, 재도전권은 기본 경제와 분리된 **별도 실험 기능**으로 검토한다.

즉, 현재 설계에서 사용자는 한 번 뽑고 결과를 확인하며,
그 판의 결과를 다시 뒤집는 구조적 구제 장치는 갖지 않는다.

## 일일 제한 정책

- 별도의 하드캡형 “하루 N회 제한”은 기본 정책으로 두지 않는다.
- 실질적인 일일 제한은 **사용자가 하루 동안 획득한 포인트 양**으로 자연스럽게 형성된다.
- 사용자는 러닝으로 얻은 만큼만 뽑을 수 있고, 추가 제한 문구를 학습할 필요가 없다.

이 방식은 사용자 경험을 단순하게 유지하면서도,
제품이 일일 루프 안에서 과도한 사용량 없이 작동하게 만든다.

## 운영 노출 정책

- 사용자에게는 복잡한 재고 정책이나 품절 UX를 기본적으로 노출하지 않는다.
- 외부에 보이는 규칙은 단순한 단일 가챠 경험으로 유지한다.
- 운영상 보상풀 조정이나 확률 조정이 필요하더라도, 사용자 경험은 가능한 한 동일한 규칙처럼 보여야 한다.

초기 단계에서는 운영 재고보다 경험 검증을 우선하되,
향후 비용/재고 제약이 강해지면 내부 운영 규칙만 추가 조정하는 방향을 우선한다.

## 보상 아이템 관리 원칙

- 보상 아이템은 백엔드에서 관리하는 별도 테이블 기준으로 운영한다.
- 보상 아이템 테이블의 최소 필드는 `title`, `imageUrl`로 둔다.
- 운영자는 API 를 통해 보상 아이템의 `title`과 이미지를 등록할 수 있어야 한다.
- 이미지 업로드 결과는 사용자 노출용 `imageUrl`로 저장/조회할 수 있어야 한다.

## 후속 시스템 설계로 넘길 결정 사항

이 문서를 기준으로 다음 시스템 설계 단계에서 풀어야 할 질문은 아래와 같다.

- 포인트 보유량과 사용 이력을 어떤 단위로 저장할지
- 한 번의 가챠 결과를 어떤 엔티티/응답 구조로 표현할지
- 카드 수와 결과 공개 상태를 서버 기준으로 관리할지, 클라이언트 연출 상태로 분리할지
- 인벤토리 포함 대상과 정렬 기준을 어떤 API 응답으로 제공할지
- 확률표와 운영 보상풀을 어떤 관리자/설정 구조로 둘지
- 보상 아이템 등록 API 와 이미지 저장 방식을 어떤 백엔드/스토리지 구조로 둘지

## 현재 합의 요약

- 가챠 포인트는 러닝으로 모으는 일일성 재화다.
- 기본 규칙은 1포인트 1회 가챠다.
- 이 가챠는 긴장감과 결과의 선명함을 우선한다.
- 꽝은 실제 꽝이며, 누적 보정 장치를 두지 않는다.
- 당첨은 희귀해야 하며, 그래서 의미가 있다.
- 재도전권은 기본 시스템에 포함하지 않는다.
- 별도의 하루 횟수 하드캡은 두지 않고, 포인트 획득량이 자연스러운 제한이 된다.
- 사용자에게 복잡한 재고/운영 정책을 직접 노출하지 않는다.
- 보상 아이템은 백엔드 테이블로 관리하며 최소 필드는 `title`, `imageUrl`이다.
- 정확한 수치 확률, 포인트 지급량, DB/API 상세는 후속 시스템 설계에서 확정한다.
