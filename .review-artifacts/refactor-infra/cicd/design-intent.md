# 설계의도

## 작업 개요

이 브랜치는 저장소 안에 OMO 전용 리뷰 파이프라인을 이식하고, 그 파이프라인이 참조할 기준 문서와 명령/스킬 구성을 함께 버전 관리 대상으로 정리하는 작업이다. 변경 표면은 애플리케이션 기능 모듈이 아니라 root 공통 설정(`.gitignore`, `.gitlab-ci.yml`), `.opencode/**` 도구 자산, 그리고 `docs/**` 문서 체계다.

## 핵심 설계 결정

### 1. 리뷰 파이프라인의 실제 로직은 `.opencode/skills/`, 진입점은 `.opencode/commands/`에 둔다
- 대안: 모든 워크플로를 단일 문서나 단일 명령 파일에 몰아넣는다.
- 선택: 재사용 가능한 단계별 로직은 `skills/`에 두고, 사용자 진입점은 얇은 `commands/` 래퍼로 분리한다.
- 이유: `write-intent`, `gen-criteria`, `create-pr-body`, `review`, `reflect-review`를 개별적으로 재사용하고 순차 오케스트레이션에서도 참조하기 쉽다.

### 2. 리뷰 산출물 계약은 `.review-artifacts/{branch-name}/` 구조를 유지한다
- 대안: 문서 산출물을 `docs/` 아래에 직접 저장한다.
- 선택: 브랜치별 산출물을 `.review-artifacts/{branch-name}/`로 분리한다.
- 이유: 브랜치 단위 리뷰 기록을 서로 섞지 않고, 파이프라인 단계 간 입력/출력 계약을 명확하게 유지할 수 있다.

### 3. `.opencode` 전체를 그대로 열지 않고 필요한 하위 트리만 추적한다
- 대안: `.opencode/` 전체를 계속 무시하거나, 반대로 전체를 통째로 추적한다.
- 선택: `.gitignore`에서 `commands/`, `skills/`, 설정 파일 등 의도된 자산만 예외로 열고 `node_modules` 같은 생성물은 계속 무시한다.
- 이유: 팀이 공유해야 하는 도구 자산만 버전 관리하고, 로컬/생성 산출물까지 섞이는 것을 피하려는 의도다.

### 4. CI의 dev/test 경로에 현재 브랜치를 한시적으로 통과시킨다
- 대안: `dev`만 유지하거나, 별도 수동 잡/변수 기반으로 테스트한다.
- 선택: `.gitlab-ci.yml`에 `DEV_TEST_BRANCH`를 추가해 `refactor-infra/cicd`도 dev/test 이미지·배포 경로를 타게 한다.
- 이유: 리뷰 파이프라인/도구 자산 정리와 함께 CI 경로를 실제로 검증하려는 목적이다. 다만 이 결정은 공유 파이프라인에 임시 브랜치 이름을 남기는 트레이드오프를 가진다.

### 5. 기존 reward 관련 계획 문서는 정리하고, 새 리뷰 파이프라인 문서 세트로 기준을 옮긴다
- 대안: 과거 계획 문서를 유지한 채 새 문서를 추가한다.
- 선택: 오래된 reward 설계/계획 문서를 제거하고, 이번 브랜치의 목표에 맞는 리뷰 파이프라인 설계/구현 문서를 추가한다.
- 이유: 현재 브랜치의 주제가 review tooling/documentation 정비이므로, 관련 없는 과거 계획 문서가 계속 남아 있으면 변경 의도가 흐려진다.

## 의도적으로 제외한 것

- `web/`, `mobile/`, `was/`, `watch/` 애플리케이션 동작 변경
- `review-pipeline-update-docs`를 핵심 6단계 auto 파이프라인에 포함시키는 일
- `reflect-review` 이전 단계에서의 소스 코드 자동 수정
- 저장소 전체 앱 빌드/배포 플로 전체 재설계

## 주의사항

- 이번 변경은 공용 `.gitlab-ci.yml`를 건드리므로, 임시 브랜치 예외가 장기 규칙으로 굳지 않도록 검토가 필요하다.
- `.opencode`를 추적 대상으로 연 만큼, 생성 산출물(`node_modules`, Python cache 등)이 함께 섞이지 않도록 ignore 경계를 엄격히 유지해야 한다.
- 이 브랜치는 문서/도구/CI 변경이 한 번에 섞여 있어 리뷰 범위가 커졌다. 리뷰 시 기능 모듈이 아니라 shared infra/process 관점으로 읽어야 한다.
- 현재 `docs/adr.yaml`에는 이번 브랜치와 직접 맞물리는 CI/tooling ADR이 없으므로, 리뷰는 설계의도와 repo convention을 중심으로 근거를 세워야 한다.
